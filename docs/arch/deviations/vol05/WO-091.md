# WO-091 deviations: ECS command buffers

## pending_entity::buffer is the open index

- Decision: `pending_entity{buffer, seq}` holds the buffer's index in open order within the queue (reset at every
  flush and clear) and the spawn command's local_seq. The entities that pending handles resolve to are always the same
  across worker counts, because playback and resolution run in key order. The `buffer` field is deterministic only when
  buffers are opened in a deterministic order. If jobs open their own buffers on workers, the open order follows
  scheduling. RT-INV-CMD-02 therefore compares the resolved entities and the seq fields across 1 to 16 workers, not
  the buffer fields. A pending handle is valid until the next flush or clear; a later queue cycle may reuse the index.
  Added a defaulted `operator<=>` on pending_entity.
- Why: the brief fixes the two u32 fields. An ordered_key (15 bytes) does not fit in one u32, and the deterministic
  rank of a buffer is not known until every buffer has been opened.
- Where: engine/runtime/include/sl/runtime/ecs/command_buffer.hpp `pending_entity`; engine/runtime/src/ecs_command_queue.cpp
  `command_queue::open`, `command_queue::resolve`.
- Rule or table: ARCH3-R118, ARCH3-R119. Open issue for WO-094 and WO-100: if pending handles must be deterministic,
  one fix is to let the owner thread open buffers in key order (open takes no memory) and bind the worker's arena at
  the first record, which needs a bind call or a worker argument on the record path. This work order does not decide
  it.

## open takes the worker; buffers are pooled; blocks come on first record

- Decision: `open(base, worker)` binds the buffer to `frame_arena::for_worker(worker)`. A job passes
  `job_context::worker()`. `open(base)` uses the owner thread's arena (`worker = arena.workers()`). open is any-thread
  under a mutex. Buffer objects are `std::unique_ptr` entries of a pool owned by the queue, reused across flushes, so
  a reference stays valid while the pool grows. A buffer takes no memory until its first record.
- Why: the brief's `open(det::ordered_key)` does not say how the buffer reaches the job's frame arena. Per-worker arenas
  bind their owner thread at their first allocation after a flip, so the blocks must be taken on the recording thread.
- Where: command_buffer.hpp `command_queue::open`; ecs_command_queue.cpp `command_queue::open`.
- Rule or table: ARCH3-R118; `thread_safety` (open is not listed; recording is worker-only and playback owner-thread,
  as listed); `ownership` command buffers.

## Blocks and their lifetime

- Decision: every block is 16384 bytes, aligned to 64, from the arena's default tag. A command header (`detail::command`,
  trivially destructible), the id and pointer arrays of a spawn_with and each payload (at most 2048 bytes) are carved
  from the current block or a new one; every piece fits one block (SL_ASSERT). Blocks are never released: the frame
  arena reclaims them when it resets the set. A queue must be flushed or cleared before its arena flips twice after the
  recording.
- Why: `limits` command_buffer_block_bytes; `ownership` "frame memory; valid until end of next frame".
- Where: engine/runtime/src/ecs_command_buffer.cpp `command_buffer::take`.
- Rule or table: ARCH3-R118, `limits` command_buffer_block_bytes, `ownership`.

## Recording failures are sticky and stop playback at their key

- Decision: the record calls return void (as in the brief). When the arena fails (out_of_memory, or the arena's own
  error) or `add`, `set`, `remove` or `spawn_with` names an unregistered type (component_unknown), the buffer records
  that code: `status()` returns it, and later records are ignored and not counted in `size()`. At flush the buffer adds
  a failure marker under key base + `size()`. Playback stops there and returns the code as is, after every command with
  a smaller key. A base with `local_seq != 0` fails the buffer with invalid_argument the same way.
- Why: the brief returns out_of_memory "as is, ops before it applied" but gives the record calls no result. A marker
  at a fixed key keeps the outcome deterministic.
- Where: ecs_command_buffer.cpp `command_buffer::fail`, `reset`, `build_index`; ecs_command_queue.cpp `command_player`.
- Rule or table: ARCH3-R019 (detectable misuse returns an error), ARCH3-R028.

## Playback outcomes and codes

- Decision: playback runs in this order. A target that is a dead entity (including the null handle), a pending entity
  with an unknown buffer or seq, one that is not a spawn, or one whose spawn has not played yet is skipped and counted
  in `skipped_stale` without a world call. A world `stale_entity` is counted the same way. `component_exists` (add)
  and `component_missing` (remove) are skipped and counted in `skipped_refused`, a field beyond the brief. Every other
  world error (out_of_memory, entity_capacity, archetype_limit, structural_change_forbidden, component_unknown) stops
  playback and is returned as is, with the commands before it applied; the flush_report of that partial flush is not
  returned. flush returns wrong_thread off the owner thread, and invalid_argument for a world of another registry or
  for two buffers with the same base key; in those cases nothing is applied.
- Why: the brief names only stale skips and out_of_memory. entity_capacity is returned by "command playback beyond
  max_entities" (`error_codes`). Refusing a duplicate base key keeps merge_ordered's Debug-only assertion from being
  the only guard.
- Where: ecs_command_queue.cpp `command_player::operator()`, `command_queue::flush`, `duplicate_keys`.
- Rule or table: ARCH3-R120, `error_codes` entity_capacity, ARCH3-R028.

## flush and clear empty the queue and destroy every payload

- Decision: each payload is move-constructed into its block when it is recorded. Playback hands it to world
  `add_raw`, `set_raw` or `create_raw`, which move from it. After the merge, flush destroys every payload, played or not,
  through `component_registry::info(id).destroy`, and empties the queue on success and on every error after the
  argument checks. `clear()` discards every unplayed command the same way, for the faulted frame of ARCH3-R028; off
  the owner thread it is a Debug assertion and does nothing. The destructor releases like clear.
- Why: world's raw calls leave destruction of the source value to the caller. The brief lists clear() separately.
- Where: ecs_command_buffer.cpp `command_buffer::release`; ecs_command_queue.cpp `command_queue::release`, `clear`,
  `~command_queue`.
- Rule or table: ARCH3-R118, ARCH3-R028.

## flush_report entries

- Decision: a spawn or spawn_with is one `spawn` entry with `component_id{}`; its components are not listed as adds.
  A destroy carries `component_id{}`. A set that adds a missing component is still reported as `set`. `resolved` holds
  (pending handle, entity) for each spawn that played, in key order. `op` has a defaulted `operator==`.
- Why: the brief lists the entry fields but not what spawn_with reports. WO-093 can read the spawned entity's
  archetype for its components.
- Where: command_buffer.hpp `flush_report`; ecs_command_queue.cpp `command_player::spawn`.
- Rule or table: ARCH3-R120, ARCH3-R129 (WO-093 builds the structural log from it).

## The merge and memory outside the blocks

- Decision: at flush each buffer fills its own `det::ordered_buffer<detail::command *>` with (base with local_seq =
  seq, command), plus the failure marker. The index is built on the owner thread and reuses its capacity. One
  `det::merge_ordered` over these buffers carries the marker comment `// neg-completion-order` on the same line.
  `world::set_phase_active(false)` holds for the duration and the previous value is restored afterwards. Memory outside
  the frame-arena blocks: the buffer pool, the per-buffer index, the merge list, the key list (all reused, global heap),
  merge_ordered's two scratch vectors and the flush_report vectors (per flush, global heap). RT-INV-CMD-04 measures the
  arena's upstream through tracking_resource counters, as the brief says.
- Why: merge_ordered takes `ordered_buffer<T>` (a std::vector, WO-084), and replay.hpp is outside paths_allowed.
  Recording itself touches only the blocks.
- Where: ecs_command_buffer.cpp `command_buffer::build_index`; ecs_command_queue.cpp `command_queue::flush`.
- Rule or table: ARCH3-R086, `determinism` merge point "command buffer playback", ARCH3-R118, ARCH3-R051.

## spawn_with checks at compile time

- Decision: `spawn_with` static-asserts at most 32 components, distinct types, component_type and nothrow
  construction from the argument. All of its memory is taken before any value is constructed, so a failed take
  constructs nothing. `spawn_with()` with no argument is `spawn()`.
- Why: world::create_with returns invalid_argument for a repeated type; a compile-time check is stronger and never
  reaches playback.
- Where: command_buffer.hpp `command_buffer::spawn_with`, `detail::distinct_types`.
- Rule or table: ARCH3-R118, ARCH3-R106.

## Names beyond the brief

- Decision: added `command_buffer::status()`, `key()` and `id()`; `command_queue::open_count()`; the constant
  `command_buffer_block_alignment = 64`; `flush_report::skipped_refused`; `detail::command`. command_buffer has a public
  constructor that takes a private passkey, so only command_queue can build one through make_unique.
- Why: tests and callers need the sticky status and the pending handle's buffer; the passkey keeps construction
  private.
- Where: command_buffer.hpp.
- Rule or table: ARCH3-R177 (no seam beyond the work order).

## No failpoint visits

- Decision: the command buffer code visits no failpoint. RFP0 reaches it through a tracking upstream of the frame
  arena or through the world's memory; RFP10 reaches it through world::create_raw. RT-INV-CMD-03 injects
  out_of_memory with testing::failing_resource, so the test runs in Release too.
- Why: the `failpoints` table names no command-buffer site.
- Where: engine/runtime/src/ecs_command_*.cpp.
- Rule or table: ARCH3-R020.

## Tests

- Decision: RT-INV-CMD-01 chains the jobs through job dependencies in a permuted order (reverse key order and two
  seeded permutations), so the completion order is exactly the permutation, on 1, 2, 4, 8 and 16 workers, plus one
  unchained run. A serial key-order model predicts each target's final state and the stale and refused counts.
  RT-INV-CMD-04 warms every per-worker arena of both sets from the owner thread before counting, as RT-INV-FRAME-04
  does, so which worker runs which job cannot move a first block allocation past the warm-up.
- Why: the brief asks for permuted completion and zero upstream allocations after warm-up.
- Where: tests/unit/runtime/cmd_playback_order_test.cpp, cmd_memory_test.cpp.
- Rule or table: RT-INV-CMD-01, RT-INV-CMD-04, ARCH3-R016.
