## Deviations

- D-099-1 (own stack): `runtime::start` cannot host a `world_link` (it owns the world and the
  system scheduler and exposes no attach point), so the demo composes the same public pieces in the
  order `runtime_lifecycle.cpp` start_jobs and start_frames use, plus the link (`stack.cpp`). The
  scene's fault report and recovery follow `runtime_recovery.cpp` (restore the newest snapshot at
  or before the fault, at most max_recoveries) in `run.cpp`.
- D-099-2 (frame-arena warm-up): the stack takes the first block of every frame-arena set before the
  first frame (owner thread, two flips). Which worker first opens a command buffer depends on
  stealing, so a lazy first block landed in arbitrary steady frames and broke ARCH3-R051's zero
  upstream count.
- D-099-3 (RFP5 on the command line): the CLI cannot arm failpoints (arming lives in
  sl_runtime_testing, R-RT-LINK), so at tick 450 the runner sets a scripted fail that lantern.decay
  returns as `ctx.fail(errc::job_failed)`, the same system_fail path RFP5 takes. gate_recovery_test
  arms the real RFP5 (testing::arm) through `demo_options::arm_fault` in builds with failpoints.
- D-099-4 (hash timeline): the hashes are `state_hash` of the world with no contributors, indexed by
  applied steps (the scene_clock resource): a restore does not rewind the logical tick (WO-089), and
  the event lists carry logical ticks, so hashing them would make every recovered or resumed run
  differ. Event state still rides in every snapshot (events_contributor).
- D-099-5 (change ticks): after a restore and before a resume the stack moves the world's change
  tick above every system's last run (`set_change_tick`), so changed<beacon> sees the restored rows.
- D-099-6 (hash file): each run also writes hashes.json (sl-runtime-hashes/1, no schema yet), the
  per-tick input of determinism_check; the directory layout is runs/<build>-w<N>-<mode>/.
- D-099-7 (demo.log): the runner writes demo.log atomically with the rest of the evidence (GATE-01
  checks it); runtime-demo.sh also tees the output there, and the runner's file replaces the tee'd
  one with the same lines.
- D-099-8 (recovery block without a fault): demo-report.json's recovery is {0, 0, true} when no
  fault ran (--ticks 450 or less); the schema requires the block.
- D-099-9 (phase wall time): frame_scheduler times phases with the platform clock, which is the
  demo's manual step_clock, so every `wall_ns` in demo-report.json is 0; `wall_ms` is real time.
- D-099-10 (steady frames): a steady frame is past warmup_frames + 1, not one of the two frames
  after a restore and not a runtime.mem report frame (frame % 600 == 0, one INFO event by design).
- D-099-11 (Fabric write rate): lantern.glow rewrites a rotating window of 8 beacons every 20 steps
  (one commit of 16 field changes): rewriting all 128 made each Debug commit cost about 0.4 s.
- D-099-12 (gate tests): each gate test runs the fresh pass only and hashes every 50 steps
  (`demo_options::variants`, `hash_every`, not on the command line) to stay within 15 s Debug; the
  full matrix is runtime-determinism's.
- D-099-13 (matrix build): the 5 x 2 matrix runs on the gcc-release demo (32 s a run; the Debug demo
  takes 506 s) and the Debug (clang) demo runs once (workers 4, parallel) as the cross_compiler
  record. Each run checks its own resume and replay against its fresh pass.
- D-099-14 (negative test scale): the patched demo runs 5000 lanterns for 120 ticks (snapshot every
  60) on workers 1 and 8; the divergence shows within that run.
- D-099-15 (timing-free planted divergence, WO-114): playing the buffers back in open order diverged only
  when jobs completed out of key order, which the founder's jail (bwrap, fewer CPUs) did not produce, so the
  negative gate failed there. The patched copy now plays the buffers in reverse open order, rotated by a
  hash of a process-wide flush serial. A fixed keyless order alone (reverse, or a seeded sort of the keys)
  would not do: it is deterministic, every row would equal the workers=1 reference and the check would
  exit 0. The serial makes a resumed or replayed pass meet other rotations at the same tick than the fresh
  pass, so the workers=1 row diverges without a second thread. The gate now requires the checker to name
  workers=1. Proven on the host, under `taskset -c 0`, and with the checker over the planted w1 run alone and
  the w8 run alone (exit 1 each, resume tick 63).
