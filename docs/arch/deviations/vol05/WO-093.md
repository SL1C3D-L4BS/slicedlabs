# WO-093 deviations: change tracking (episode 095)

## tick_after is the query filter rule

- Decision: `tick_after(tick, since)` is `int32(tick - since) > 0`, the same rule as the query filters' tick compare
  (WO-090), and is constexpr so callers and tests share one definition.
- Why: ARCH3-R131 asks for a wrap-safe compare; two different rules would let a query and a helper disagree.
- Where: engine/runtime/include/sl/runtime/ecs/change.hpp `tick_after`.
- Rule or table: ARCH3-R128, ARCH3-R131.

## mark_changed returns result<void> and finds the row by scanning chunks

- Decision: `mark_changed<T>(world&, entity, tick)` (and `mark_changed_raw` by component id) returns `result<void>`
  with stale_entity, component_missing or component_unknown; it stamps the changed tick of exactly one row. The row
  is found from the address `get_raw` returns, by scanning the chunks of the archetypes that hold T. It does not
  check that the caller declared a write of T; that guard belongs to the scheduler (WO-094).
- Why: the brief gives no return type, and a silent no-op on a stale handle would hide bugs; world.hpp has no
  public entity-to-row lookup, and this work order may not edit it. The cost is the chunk count of archetypes
  holding T.
- Where: change.hpp `mark_changed`, `mark_changed_raw`; engine/runtime/src/ecs_change.cpp.
- Rule or table: ARCH3-R128, ADR-0009.

## last_run_ticks: fixed slots keyed by phase and system index

- Decision: 2048 fixed slots keyed by `last_run_key(phase, system_index)` = phase * 256 + index; `record` with an
  out-of-range key is ignored; `since` of a never-run system is the floor, initially 0xFFFFFFFF, so the first run
  sees every row stamped at tick 0 or later; `entries()` and `restore(entries, floor)` save and load
  it for snapshots; `sweep(now)` clamps it like the world's ticks.
- Why: the brief names the helper but not its keys or size; fixed storage keeps it allocation-free on the hot path
  (ARCH3-R174); snapshots need the bookkeeping to replay changed<T> the same.
- Where: change.hpp `last_run_ticks`, `last_run_key`, `last_run_slots`; ecs_change.cpp; ecs_change_sweep.cpp.
- Rule or table: ARCH3-R128, ARCH3-R174.

## Exactly-once needs the change tick to advance between conflicting runs

- Decision: the tests give every system run its own change tick; with that, a reader sees each write exactly once
  across frames (RT-INV-CHG-01). If a writer and a reader share one tick, a write after the reader in the same tick
  is missed.
- Why: changed<T> compares `stamp > since`; equal ticks cannot order a write against a read.
- Where: tests/unit/runtime/chg_changed_test.cpp; consumer is the scheduler (WO-094), whose brief sets
  write_tick = world tick (open issue for WO-094).
- Rule or table: ARCH3-R128.

## Signal contents and order

- Decision: `structural_log::append(flush_report, world)` emits, per batch, first `archetype_created` for every
  archetype new since the last append (in creation order), then one signal per applied op in playback order:
  spawn -> entity_created, destroy -> entity_destroyed, add -> component_added, remove -> component_removed. The
  `archetype` field is the entity's archetype at the boundary after the flush, or `no_archetype` if it is dead.
  Appending for another world, or after a restore (generation not matching the count), re-announces every
  archetype. Signals stay until `clear()`; the flush hook (WO-094) calls append and clear.
- Why: flush_report records no per-op archetype, so the boundary state is the only exact one; a restore can
  reorder archetypes.
- Where: change.hpp `structural_log`, `change_signal`, `change_signal_kind`; engine/runtime/src/ecs_change_log.cpp.
- Rule or table: ARCH3-R129.

## A set entry gives no signal

- Decision: a `set` op in flush_report produces no signal, even when it added the component (the world version
  still moves; RT-INV-CHG-04 tests this).
- Why: flush_report reports a set that adds as `set`, so the log cannot tell it from a replace. Open issue for
  WO-091/WO-100: report a set that adds as `add`.
- Where: ecs_change_log.cpp `kind_of`.
- Rule or table: ARCH3-R129, ARCH3-R130.

## Tick-wrap sweep: clamp age 2^30 - 1, every 2^30 ticks

- Decision: `sweep_ticks(world, now)` clamps every added and changed stamp older than `change_tick_max_age`
  (2^30 - 1) to `now - change_tick_max_age`; callers sweep when `sweep_due(last_sweep, now)` (every
  `change_tick_sweep_every` = 2^30 ticks). `sweep_ticks` itself sweeps unconditionally; a fast-forwarded clock must
  sweep before the jump exceeds the period.
- Why: the literal "clamp ticks older than 2^31" lets stamps age past 2^31 between sweeps and misorder. With clamp
  age plus sweep period at most 2^31, every live stamp stays under 2^31 old and the int32 compare is exact.
- Where: change.hpp `sweep_ticks`, `sweep_due`, `change_tick_max_age`, `change_tick_sweep_every`;
  engine/runtime/src/ecs_change_sweep.cpp.
- Rule or table: ARCH3-R131; limits table (change tick rows).

## Document writes stamp changed = 0

- Decision: none here; the tests accept WO-088's stamp. A document add stamps changed = 0, which reads as fresh
  when the tick nears 2^31 past 0.
- Why: world.hpp owns the stamp. Open issue for WO-088/WO-097.
- Where: tests/unit/runtime/chg_added_test.cpp.
- Rule or table: ARCH3-R127, ARCH3-R131.

## Names beyond the brief, failpoints and thread safety

- Decision: added names are `sweep_due`, `last_run_key`, `last_run_slots`, `change_tick_max_age`,
  `change_tick_sweep_every`, `mark_changed_raw` and `last_run_ticks::entry`. No failpoints (nothing allocates or
  fails except the handle checks). mark_changed may run from parallel batches on distinct rows (tested);
  last_run_ticks, structural_log and sweep_ticks are owner-thread only, and structural_log does not check the
  owner thread itself.
- Why: the brief leaves these open; the boundary hooks that call them already run on the owner thread.
- Where: change.hpp.
- Rule or table: ARCH3-R175, ARCH3-R177.
