## RFP5 moves after the system body

- Decision: the RFP5 visit in `system_scheduler::run_system` now follows the body (and the last-run record); before
  WO-109 it preceded the body, so the body never ran. sched_access_guard_test's RFP5 case now expects one run.
- Why: item 5 sets the site to "ecs::system_scheduler after a system body", and the failpoints outcome ("visited
  after the system body returns") and WO-094's deviation entry say the same; the code was the only source that
  visited before the body. A failed system's phase playback is discarded either way (`end_phase`).
- Where: engine/runtime/src/ecs_system_scheduler.cpp `system_scheduler::run_system`;
  tests/unit/runtime/sched_access_guard_test.cpp.

## The system scheduler keeps last runs in last_run_ticks

- Decision: `system_record::last_run` is gone; `system_scheduler::last_runs()` is an `ecs::last_run_ticks` keyed
  `last_run_key(phase, system_index)`. A system's run reads `since(key)` and records its write tick in its own slot
  from its worker; capture, restore and sweep happen on the owner thread between frames. A first run now reads the
  floor (0xFFFFFFFF, one before tick 0) instead of 0, so it sees stamps of tick 0 as R128 says.
- Why: item 9 (R128). Distinct systems write distinct array elements, so concurrent runs do not race.
- Where: engine/runtime/include/sl/runtime/ecs/system.hpp `system_scheduler::last_runs`;
  engine/runtime/src/ecs_system_scheduler.cpp `run_system`; tests sched_order_test.cpp, chg_wrap_test.cpp.

## A restore rewinds the logical tick and the last runs

- Decision: a runtime recovery point is the snapshot plus `last_runs().entries()` and `floor()` at its tick
  (`runtime::recovery_point`, in memory). `restore_snapshot` restores the world and contributors, then
  `last_runs().restore` and `frame_scheduler::rewind_logical(snapshot tick)`; the frame clock and the stepper keep
  their state (wall time goes on). A swap rollback uses the same restore. engine/runtime/tools/demo keeps its own
  recovery and its change-tick move (the brief says it may drop it; it is not needed for the runtime fix).
- Why: item 7 (R029, R145). The runtime's recovery snapshots never leave memory, so the last runs need no new
  snapshot contributor; time_contributor.cpp is unchanged because the frame scheduler owns its clocks privately and
  only the logical tick is rewound.
- Where: engine/runtime/include/sl/runtime/frame.hpp `frame_scheduler::rewind_logical`;
  engine/runtime/src/runtime_recovery.cpp `take_snapshot`, `restore_snapshot`; tests life_recovery_test.cpp,
  snap_continue_test.cpp, life_background_test.cpp and life_fault_isolation_test.cpp (now == restored tick).

## A faulted frame neither delivers nor flips its events

- Decision: `frame_scheduler::set_frame_faulted(bool)` and `frame_faulted()` (owner thread; every frame starts
  unmarked) instead of a `boundary_context` flag: attach's hooks already hold the scheduler. The runtime marks the
  frame from the phase end that sees a fatal report or a failed system (`discard_after_fatal`), on a playback
  out_of_memory (`on_phase_end`) and at fault_check; deliver is then skipped, and at arena_flip the channel keeps both
  lists and drops the undelivered writes (`event_stream::drop_pending`). A successful restore unmarks the frame: the
  restored lists are the snapshot's, taken before that frame's flip, so the flip must still run.
- Why: item 2 (R028). Under stop the older list now survives the faulted frame; the restore path is unchanged.
- Where: engine/runtime/include/sl/runtime/frame.hpp, events.hpp `drop_pending`; engine/runtime/src/event_channel.cpp
  `deliver_hook`, `flip_hook`; runtime_fault.cpp; tests evt_lifetime_test.cpp and life_fault_isolation_test.cpp.

## The startup RFP0 sweep and its limit

- Decision: a clean start visits RFP0 three times; the new case asserts that count and fails visit 1 (root block) and
  visit 3 (the world's location page table), each unwinding to Created with no thread or tracked byte and a working
  retry. Visit 2 (the entity allocator's page list, std::pmr) aborts by design and is not swept; the job system
  allocates nothing tracked; failing_resource cannot wrap the runtime's own resources. The limit is written into
  ARCH3-R025.
- Why: item 4. A fork-based probe (not committed) showed visit 2 ends in SIGABRT and visits 1 and 3 in
  out_of_memory.
- Where: tests/unit/runtime/life_startup_unwind_test.cpp; SL-ARCH-003 ARCH3-R025.
